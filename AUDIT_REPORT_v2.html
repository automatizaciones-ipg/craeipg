FLUJO DE AUTENTICACIÓN GOOGLE OAUTH 2.0

  Alumno → clic "Continuar con Google"
       │
       ▼  (auth-astro/client → signIn("google"))
  Google OAuth Consent Screen
       │  (solo muestra cuentas @ipg.cl / @alumnos.ipg.cl en el scope)
       ▼
  auth.config.ts → callback signIn()
       ├─ profile.email.endsWith("@ipg.cl")      → true  → sesión creada
       ├─ profile.email.endsWith("@alumnos.ipg.cl") → true  → sesión creada
       └─ cualquier otro dominio               → false  → BLOQUEADO
       ▼
  middleware.ts → en cada request protegido
       └─ getSession() → verifica token JWT firmado con AUTH_SECRET
          → allowedDomains.some() → double-check de dominio en edge

Análisis de Seguridad

Auditoría multicapa — autenticación, autorización, secretos, cabeceras HTTP y mitigaciones

Autenticación

A+

Google OAuth 2.0 via auth-astro. Doble validación de dominio:

  • auth.config.ts → callback signIn() bloquea dominios no institucionales
  • middleware.ts → en cada request, verifica JWT + dominio nuevamente
  • Desarrollo local: bypass via isDev para facilitar trabajo sin OAuth real

Proxy de Archivos Drive

A+

Ningún archivo de Google Drive se expone directamente al navegador:

  • Service Account genera JWT RS256 con jose (5 min TTL)
  • Access token nunca llega al cliente — todo fluye edge → Drive → cliente
  • Cache-Control: no-store en respuestas de descarga
  • Sesión verificada antes de cada descarga

Credenciales de Plataforma

A

Contraseñas Moodle e institucionales ya NO están hardcodeadas en JSX:

  • /api/platform-info → sesión requerida → Cache-Control: private
  • Componentes fetchen al montar con useEffect, muestran •••••••• mientras carga
  • Único punto de cambio de credenciales: platform-info.ts

Panel de Administración

A+

Doble barrera de acceso al panel de auditoría:

  • Astro SSR verifica ALLOWED_ADMINS antes de renderizar la página
  • /api/admin/logs vuelve a verificar en el servidor — defensa en profundidad
  • Single source of truth: src/lib/admins.ts (no duplicados)

Inyección en Búsqueda Drive

B+

Mitigación básica de caracteres especiales en query:

  • queryParam.replace(/'/g, "\\'") — escapa comillas simples
  • Drive API no soporta SQL injection real — bajo riesgo
  • Sesión requerida → solo usuarios autenticados buscan
  • Mejora sugerida: sanitización más robusta con allowlist de caracteres

Gestión de Secretos

B

Estado mixto — la mayoría bien, uno expuesto:

  • AUTH_SECRET, GOOGLE_DRIVE_PRIVATE_KEY, GOOGLE_CLIENT_SECRET → Cloudflare Secrets ✓
  • GOOGLE_CLIENT_ID → en texto plano en wrangler.jsonc ⚠
  • GOOGLE_DRIVE_CLIENT_EMAIL → en texto plano en wrangler.jsonc (baja criticidad)
Vector de Ataque Mitigación Implementada Nivel
Acceso sin autenticación Middleware SSR verifica JWT en cada request; redirect a / si falla Alto
Descarga directa de archivos Drive URLs de Drive nunca expuestas; proxy edge con token de corta vida (5 min) Alto

Issues Priorizados

Listado completo de problemas detectados — ordenados por impacto y criticidad

P2 · Seguridad

XSS potencial en consola de auditoría (innerHTML dinámico)

En admin/index.astro los logs se renderizan con tbody.innerHTML = logs.map(log => `...${log.name}...${log.fileName}...`). Si un alumno descarga un archivo con nombre malicioso como <img onerror="...">, y el admin recarga la consola, el script se ejecuta en el contexto del admin.

Fix: Reemplazar interpolación directa por document.createTextNode() o usar el.textContent = log.name al construir las celdas, o sanitizar con log.name.replace(/[<>"]/g, c => '&#'+c.charCodeAt(0)+';').

P2 · Secretos

GOOGLE_CLIENT_ID expuesto en wrangler.jsonc (texto plano en repositorio)

wrangler.jsonc contiene el Client ID de Google OAuth en texto plano bajo "vars". Si el repositorio alguna vez se hace público o se sube a GitHub, este ID queda expuesto. Si bien el Client ID por sí solo no permite acceso, en combinación con otros datos puede facilitar ataques de phishing OAuth.

Fix: Mover a Cloudflare Secret: wrangler secret put GOOGLE_CLIENT_ID. Reemplazar en wrangler.jsonc por un placeholder o eliminar la clave de "vars".

P3 · Arquitectura

StudyTechniques.tsx exporta DigitalTools — confusión semántica y duplicado

src/components/StudyTechniques.tsx importa y re-exporta el componente DigitalTools (hub de 8 herramientas). Esto significa que la ruta /tecnicas-estudio muestra el mismo hub de herramientas digitales que /herramientas-digitales, con el mismo contenido. El ResourceGrid lleva a /tecnicas-estudio con título "Técnicas y Estrategias de Estudio" pero el contenido es incorrecto.

Fix: Crear un componente StudyTechniques.tsx real con secciones de técnicas de estudio (infografías, CRAI PDF, video). Los 5 Drive IDs están disponibles — solo falta el componente UI. Ver §4 "Recursos sin integración".

P3 · Contenido

PracticaLaboral.tsx sin archivos Drive reales — botones no funcionales

El componente PracticaLaboral.tsx tiene UI completa (etapas, cards interactivos) pero el array downloads apunta a archivos inexistentes en Drive. Los botones de descarga presentan UI pero fallan en el edge.

Fix: Luis debe subir los documentos de práctica laboral a Google Drive y compartirlos con el Service Account. Luego actualizar los Drive IDs en el componente.

P3 · Contenido

5 archivos en Google Drive sin sección UI correspondiente

Existen 5 archivos en la carpeta Drive que no tienen presencia en ningún componente: aprende_mas_CRAI_IPG.pdf, 3 infografías de estudio, y el video de comprensión lectora. Representan contenido valioso que los alumnos no pueden acceder.

Fix: Implementar un StudyTechniques.tsx real (ver issue anterior) que incluya estos recursos.
